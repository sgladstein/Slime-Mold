# Mould simulation at scale: plan forward (2026-11-10)

Plan only, nothing built. Asked for by the owner on 2026-11-10 after the
Jenson review ([`jenson-physarum-2026-11-10.md`](jenson-physarum-2026-11-10.md)):
"a comprehensive plan forward, including GPU development, not just the 5
cheapest tests", and whether more research is needed. Repo copy of the live
doc https://claude.ai/artifact/NhwbErNYntvbu53kh39szf (the doc has the
roadmap drawn; here it is a list). Owner's standing goal: interesting
simulations that can become a game, not realism.

## The plan in brief

Move the mould's walkers and trail onto the GPU so a dish can hold hundreds of thousands to millions of walkers, and keep the game's rules, scoring and tools on the CPU reading a coarse copy of the GPU's fields. Get there in six gated phases. The first two are cheap and tell us whether the big version is worth building before any GPU code is written.

1. **Foundations on the CPU.** Add a dish hash and a determinism test. Write the new rules (contagion, more than one walker per cell, parameters that depend on density) as plain CPU code that later serves as the reference for the GPU.
2. **See the scale before building it.** Render big dishes offline on the CPU, slowly, and pick a target scale and look from blind A/B pages.
3. **GPU sandbox.** A new binary with walkers, trail, drawing and the lamp and oats on the GPU, and no game.
4. **Game rules on the GPU sim.** Food, sleep, births and deaths on the GPU; census and scoring on the CPU from a coarse readback. One existing dish ported end to end.
5. **Port and retune every dish**, with CI running the GPU path in software.
6. **New play that only scale allows:** contagion as a tool, growth fronts, sweeping events, territory, a large world.

**On research: the reading for the design is done; one targeted pass is still needed before writing GPU code.** The papers and Jenson's work are read in full. What has not been read is any implementation's actual source: so far only READMEs. Reading three codebases (Bleuje, Lague, PolyPhy) is the first task of phase 3, and Jones 2011 is needed before porting growth and shrinkage.

## The GPU design

The GPU owns everything there are millions of (walkers and fine fields); the CPU owns everything there are a few of (piles, tools, pieces, the score) and reads the GPU's state through a coarse copy a few times a second. That split keeps today's census and scoring code nearly unchanged.

**On the GPU, each step, as compute passes sharing the device pixels already opened:**

1. **Sense, turn, move**, one thread per walker: read the trail and scent at three sensors, turn by Jones's rule, step. The parameters that today are constants become per-walker or per-cell where a rule needs it: density-dependent reach (36 Points), stochastic steering (MCPM), infection (contagion). The lamp's push becomes a force field the move reads.
2. **Deposit and count**: each walker adds trail into its cell with an integer atomic add, and adds itself to a per-cell count. Integer adds give the same total in any order, so the step stays deterministic. More than one walker per cell is allowed; Jones's "gel" rule becomes an option that limits the count instead of blocking moves.
3. **Diffuse and decay**, one thread per cell: the 3x3 mean and the keep factor for trail, scent and the contagion channel, with salt and the rim as walls.
4. **Economy**, one thread per walker: eat from piles (pile totals in a small atomic buffer), pay upkeep, sleep, starve. Births and deaths go through a fixed pool of walker slots, compacted by a prefix sum, so the slot order does not depend on thread timing.
5. **Draw**, a fragment shader straight from the fields to the window: brightness from trail, the food ramp, wet and sleep, walkers as specks if wanted. This also removes the 3.83 ms the CPU spends drawing today.

**On the CPU:** tools write small patches into GPU buffers (lamp position, oats, salt strokes, snip lines). Four times a second, a coarse readback (for example the trail max-pooled to 256 x 160, plus food and walker counts per coarse cell) feeds the existing census, pieces, joins, scoring and HUD. The readback arrives a frame or two late, which the census does not notice.

**Two grids.** The simulation grid can be four times finer each way (1024 x 640, about 650,000 cells) or more, while game rules keep measuring in the coarse cells they use today. That is what makes thin tubes and hundreds of loops possible without rewriting the rules.

**Determinism and tests.** Each walker gets its random numbers from a hash of seed, walker id and step, so nothing depends on scheduling. On one machine a seed gives the same dish every time; across GPU vendors floats can differ in the last bits, so census tables say which machine they ran on. The phase 1 CPU code stays as the reference: a test runs a small dish on both and compares fields within a tolerance. CI runs the GPU path on Mesa's software Vulkan driver (lavapipe), slowly and at small sizes, because CI has no GPU.

## Phases

Each phase ends on a gate with a named measure, judged the repo's way: pictures first, then paired seeds against idle and random hands, with frame cost quoted.

**1. Foundations on the CPU**

- Add a dish hash and a determinism test, the first item in the Pixel_Physics review, so every later speed-up can be proved to change nothing.
- Add a frame profiler that splits simulation, drawing and readback.
- Add the new rules to `Params`, all off by default:
    - contagion: a mark bit per walker plus a short-lived signal field;
    - a crowd limit N per cell, with N = 1 meaning today's rule;
    - sensor reach set by local trail density;
    - a stochastic steering exponent.
- **Deliverable:** the rules with tests, and a picture page at today's scale. The crowd-limit change goes up as a blind A/B.
- **Gate:** with every flag off, the dish hash and every census table are unchanged. The contagion front stops at a snip on 16 of 16 seeds. Frame cost is quoted for each rule.

**2. See the scale before building it**

- Add an offline example that runs phase 1's rules on 1024 x 640 and 2048 x 1280 with 100,000 to 1,000,000 walkers. It uses all CPU cores and is slow on purpose: minutes per GIF, not frames per second. It sweeps walker count, crowd limit, angles and the density rule.
- Run the lamp and oats on the same big dishes. The 2026-11-10 review found the lamp's effect gets lost in the mould's own rewiring at 22.5 degrees, and a finer network could make that worse.
- **Deliverable:** a blind A/B page with today's dish against three or four scaled versions, next to Jenson's clips. It shows what a tool does at each scale.
- **Gate:** the owner picks a target grid, walker count and look, or decides it isn't worth it. If it isn't, stop here and take the Pixel_Physics multi-core renderer instead.

**3. GPU sandbox**

- Read the Bleuje, Lague and PolyPhy code.
- Add `--bin mouldgpu`. It runs compute passes 1-3 and the draw pass on the device pixels already holds; checking that pixels 0.17 exposes its device and a custom render hook is the first task.
- Lamp, oats and salt work as field writes. Presets come from 36 Points-style parameter sets, and contagion is on a key.
- Measure frame time with GPU timestamps. Add the CPU twin test and a lavapipe CI job.
- **Deliverable:** a toy the owner can play with at the chosen scale, with GIFs on a page.
- **Gate:** the chosen scale runs at 60 frames a second with the GPU busy under half the frame on the owner's machine. The same seed gives the same pictures twice, and the twin test passes.

**4. Game rules on the GPU simulation**

- Port the per-walker food, upkeep, sleep and starvation. Piles keep their totals in atomics. Births and deaths go through the slot pool, with Jones 2011's crowd and sparse windows from the per-cell counts.
- The rival mould becomes a second trail channel.
- The coarse readback feeds the existing census and score.
- Port one dish end to end: Running Dry, which leans hardest on the food economy.
- **Gate:** on 16 paired seeds the ported dish keeps its shape. The plan hand wins, while idle and random lose, with sign-test p quoted. The frame budget still holds.

**5. Port and retune every dish**

- Port the lesson, the three challenge dishes, Keep It Alive and The Wild One.
- Re-derive every constant measured in cells (`TUBE_WIDTH`, `OATS_PULL`, star bars) and point `mouldprobe` at the GPU path.
- Keep the CPU path until this gate passes, then decide whether it stays as a small-dish fallback.
- **Gate:** every dish meets its ship bar on 16 seeds, and the owner plays them and prefers them.

**6. New play that only scale allows**, each with its own report and census:

- contagion as a tool: an alarm that pulls mould back, or a feast that lets it grow;
- growth fronts as the thing you feed, as in network_2;
- sweeping events, as in the explosion clip;
- territory between two pattern regimes, which is Bloomfront's ground;
- a large scrolling world, the forest floor from above;
- drying into a sclerotium.

**How this sits with work already queued:**

- Playing Keep It Alive and The Wild One, and tracing Keep It Alive's luck, are independent of all this; they can happen any time.
- From the Pixel_Physics review, take the dish hash and the determinism test now (phase 1). Hold the multi-core renderer port until the phase 2 gate, because GPU drawing would replace it.
- Bloomfront's Stage 0 tests design risk on today's CPU dish and can run alongside. Its two-mould step moves to the GPU in phase 4.
- The forest floor wants a large world. It is best built after phase 3 if the GPU goes ahead, or small on the CPU if not.

## Roadmap

Phases run in order and each starts only when the gate before it passes. Phase 2's gate is the one real fork: it is where the owner sees the big mould and decides whether to build it.

1. Foundations on the CPU. Gate: flags off gives the same dish hash; contagion stops at a snip.
2. See the scale. Gate: the owner picks a target scale, or stops and stays on the CPU.
3. GPU sandbox. Gate: 60 fps with the GPU under half a frame, repeatable.
4. Game rules on the GPU. Gate: plan wins, idle and random lose, on 16 paired seeds.
5. Port every dish. Gate: every ship bar met, and the owner prefers it in play.
6. New play from scale. Each idea gets its own report and census.

## Risks and the owner's decisions

The biggest risk is not the GPU code. It is whether the player's hand still shows in a mould a hundred times busier, which is why phase 2 asks that question with pictures before anything is built.

| Risk | Why it matters | What the plan does about it |
| --- | --- | --- |
| Tools get lost at scale | A finer, livelier network rewires around the lamp; the 2026-11-10 review saw this at 22.5 degrees | Phase 2 shows the lamp and oats on the big dishes before the gate |
| Game rules on the GPU | Food, sleep, births and deaths per walker are the hardest part to make parallel and deterministic | Phase 4 ports one dish first; slot pool with prefix-sum compaction; integer atomics only |
| Results differ between machines | GPU floats can differ across vendors in the last bits | Census tables name the machine; the CPU twin test bounds the difference; CI runs in software |
| The owner's GPU is unknown | The frame budget in phase 3 depends on it | Decision 2 below |
| Retuning | Every constant in cells moves with the finer grid | Phase 5 re-derives them dish by dish against the probe |
| Two code paths for a while | The CPU and GPU versions can drift apart | The twin test, and phase 5 decides whether the CPU path stays |
| Licences | Bleuje (CC BY-NC-SA) and Lague (GPL-3.0) cannot be copied into proprietary code | Read for ideas only; PolyPhy (MIT) can be reused with its notice |

**Decisions that are the owner's:**

- [ ] Upload Jones 2011 (*Natural Computing*, growth and shrinkage) before phase 4.
- [ ] Hold the Pixel_Physics multi-core renderer port until the phase 2 gate? Recommended, because GPU drawing would replace it.
- [ ] At the phase 2 gate: the target scale and look, or stop.
- [ ] At the phase 5 gate: does the GPU version replace the game, or sit beside it as a separate mode?
